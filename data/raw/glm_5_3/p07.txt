# Post-Incident Analysis: Stale Account Balances Served for 47 Minutes

## Summary

During a recent incident, customers in one region saw account balances that did not reflect their most recent transactions. The degradation lasted 47 minutes. Throughout the incident, the primary database was fully healthy, all writes committed successfully, and the service reported nominal availability and latency. The root cause was not a component failure but an interaction among three normally benign mechanisms: a retry policy designed to keep the service available during transient origin problems, a read-through regional cache whose expiry timestamps were computed by calling hosts, and a single deployment host whose system clock ran ahead of true time. No data was lost or corrupted; the correct balances existed in the database at all times. The failure was one of read freshness, which is precisely why our monitoring, oriented toward availability and error rates, did not catch it.

## The Skewed Host

The incident began with an otherwise unremarkable deployment. One newly launched host in the regional pool had a clock that ran meaningfully ahead of true time. The host had been provisioned from a paused machine image, and its time synchronization daemon had failed to correct the drift before the host was admitted to serving traffic. Nothing in our admission checks or runtime telemetry compares a host's clock against a trusted time source, so the skew went entirely unnoticed. The host passed health checks, served traffic, and computed timestamps like any other node. Every timestamp it produced, however, was shifted into the future, and one of those timestamps would later determine how long a set of cached balances was considered fresh.

## The Cache and the Retry Policy

The account balance read path is served through a regional read-through cache. On a miss, the service fetches the balance from the database and stores it in the cache with an expiry timestamp. Critically, that expiry is computed by the calling host as its local notion of "now plus the intended lifetime," and the cache servers honor the embedded timestamp rather than enforcing a server-side TTL. This design choice, made years ago to allow per-key lifetime tuning, means the integrity of cache freshness depends on every calling host having a correct clock.

Layered on top of this is a retry policy intended to ride out brief problems reaching the database. When an origin fetch fails, the service retries a bounded number of times. If all attempts fail, it falls back to serving the most recently cached value so that customers see an answer rather than an error. As part of this degraded-mode behavior, the fallback path also re-populates the cache with the value it just served. The reasoning was defensive: if the origin is unreachable for a while, keeping the last known value resident avoids a thundering herd of misses when connectivity returns. In normal operation this is harmless. Combined with a skewed clock and an invalidation race, it became the mechanism that resurrected stale data.

## The Trigger and the Race

The triggering event was a brief network interruption between the service tier and the database. The database itself remained healthy throughout; it simply became momentarily unreachable from the region. Read-through fetches began failing, the retry policy engaged, and the fallback path started serving cached balances and writing them back into the cache with freshly computed expiry timestamps.

Two things then went wrong together. First, a meaningful fraction of these fallback writes were handled by the clock-skewed host, so the entries it re-populated carried expiry timestamps pushed far beyond their intended lifetime. Second, during this same window, customers were successfully making transactions. The write path updates the database and then invalidates the corresponding cache entry, which is how fresh balances normally propagate. But the fallback path was concurrently writing the old balance back into the cache. When a fallback re-population landed just after an invalidation for the same account, the stale value was resurrected, now stamped with an inflated expiry that the cache would trust. When network connectivity to the database was restored, all systems looked recovered. Fetches succeeded, health checks passed, and the database had the correct balances. But the affected cache entries were considered valid well into the future, so reads continued to be served from them. Customers saw outdated balances until we intervened.

## Why Monitoring Failed

Our monitoring failed for a structural reason: it measures whether the system is up and fast, not whether it is correct. The database dashboards were green because the database was genuinely fine. Service-level success rates stayed high because serving a stale balance is, from the protocol's perspective, a successful request with normal latency. Our cache dashboards actually looked better than usual during the incident, since the fallback path inflated hit rates, and elevated hit rate has always been read internally as a positive signal. There was no metric tracking the age of cache entries relative to their intended lifetime, no continuous comparison of cached values against origin values, and no alert on host clock skew. The first genuine signal came from human channels: customer reports of missing transactions, followed shortly by an internal reconciliation job that flagged divergence between cached reads and database state. We were alerted by the consequence rather than the cause.

## Immediate Mitigation

Once reconciliation identified the affected account keys, mitigation proceeded in three steps. We purged the stale entries from the regional cache, which immediately restored correct balances on the next read. We cordoned the clock-skewed host out of the serving pool and corrected its clock before returning it to rotation. Finally, we disabled the fallback re-population behavior through configuration, accepting that origin outages would now surface as errors rather than silently extended staleness. All three actions were completed within the incident window, and the total customer-facing duration was 47 minutes.

## Durable Prevention

The permanent fixes address each link in the causal chain. Cache expiry will become server-authoritative: the cache will assign TTLs using its own clock, and calling hosts will lose the ability to embed expiry timestamps, so no single bad clock can extend freshness. The retry fallback will be bounded by a maximum staleness that no number of retries can extend, and fallback reads will never write back to the cache, eliminating both the resurrection mechanism and the invalidation race. Invalidation will additionally be hardened with versioned entries so that a late-arriving stale write cannot overwrite a newer value.

On the observability side, we are adding clock-skew monitoring with alerting on every serving host, and hosts exceeding a skew tolerance will be automatically removed from rotation. We are adding a freshness check that continuously samples accounts, compares cached reads against origin reads, and alerts on divergence. Cache entry age will become a first-class metric. Finally, we will run a game day that combines an origin connectivity blip with an injected clock skew, because this incident taught us that our defenses were tested one fault at a time, while reality delivered two at once.
